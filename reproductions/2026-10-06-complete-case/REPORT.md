# 完整案例：异常点会不会让预测更差？

2026-10-06。这次在 LabCouncil 页面中跑完了一个完整周期：第一轮工作 → 定时准备材料 → 实际模型追问 → 保存草稿 → 确认第二轮方向 → 后台继续 → 第二轮组会快照。**流程与数值核验通过，模型报告的事实表述未通过。** 数据是合成的，角色和一次问答使用真实 DeepSeek Flash；评审方向是明确标注的 Codex 工程 fixture，不是用户本人给出的科研评审。

## 先用普通话看结果

任务是让一条拟合直线预测新数据，和“永远猜训练数据的平均值”比较。第一轮数据干净；组会后只给部分测试标签加入很大的偏差，训练数据保持不变。

同一个 seed7 的平方误差从约 **0.17 增加到 10.16**，说明这个误差指标会受到少量大偏差的明显影响。中位数绝对误差只从约 **0.24 变成 0.27**：它更接近大多数点的典型偏差。第二轮另外两个重复也得到相近的误差。拟合直线在保存的三个指标上仍优于只猜均值，但这只涉及这个合成例子，不能推出真实研究问题上的方法优势。

## 测试暴露的问题

第一轮报告说“尚未多指标检查”，但工具已经计算三种指标。我们保留原文，在唯一一次真实组会追问中指出矛盾；Flash 承认表述不准确，解释已计算的指标与未检查的稳健性范围。完整输入和答复见 [第一轮组会](meeting-01.json)。追问没有改变任务。

第二轮的计算角色仍写：**“本轮在干净合成数据上……”和“尚未加入异常点”**。复核角色的 limitations 也写“本轮仅覆盖干净测试数据，尚未加入约一成异常点”。这与保存的数据和工具输入直接矛盾。数值复算实际包含异常点，并通过独立检查；两个模型的文字错误没有被角色间复核发现。第一轮追问纠正也没有保证第二轮报告正确。

原始报告没有被改写。页面在报告旁显示工具实际输入，并说明数值复算不保证文字正确。后续代码为计算、复核和组会问答显式传递场景参数；这是针对上下文遗漏的修订，**仅经过离线 fixture 测试，尚未用新的真实请求验证效果**。本次没有超过预设额度追加模型纠错请求，也没有宣称平台已具备自动语义审查。

## 完整循环实际做了哪些事

1. 在真实页面新建真实案例。每轮三个角色，分别实际请求数据准备、回归计算、独立复算工具；平台核对允许的工具和参数后才执行。
2. 第一轮六次模型请求完成，工具保存40个训练点、100个独立测试点和三个误差指标。模型报告与原始响应分别保存。
3. Codex 用本地配置接口设置一次到时安排，worker 准时冻结第一轮材料；[定时输入](schedule-input.json)是工程测试输入，未冒充用户设定。
4. 在实际组会页面追问上述报告矛盾，真实 Flash 回答并引用快照证据。讨论不派单。
5. 页面保存标有“Codex 工程评审 fixture，不是用户科研评审”的草稿；项目仍为第一轮。点击确认后，唯一决定将计划更新到第二轮。
6. 浏览器没有执行计算；独立 worker 继续第二轮六次实际请求，生成三个重复的异常点数据及复算结果。随后用页面打开第二轮组会，保存固定快照。
7. 重放第一轮完全相同的确认请求，返回原决定，新增任务为0。第二轮追加追问因真实问答额度已用完返回409，新增模型请求为0。
8. 实际停止并重新启动该案例的网页与 worker。整个项目状态相等，六份证据、两场组会、一次讨论、一个决定与13次调用均保留。所有13个请求入口和3个独立工具记录入口读取成功。

守卫及重启证据：[restart-and-guards.json](restart-and-guards.json)。实际页面截图：[第二轮项目](project-round-02.jpg)。

## 模型、预算和来源

实际请求共 **13次**：后台12/12，问答1/1；全部HTTP200，响应模型字段均为 `deepseek-flash`。供应商返回已知总用量 **9801 tokens**，未知usage为0；人民币费用未知。temperature0、thinking disabled、每次输出最多768 tokens、输入最多20000 UTF-8字节、请求超时40秒，无自动重试。次数硬上限在发送前事务预留；这不是项目 token 或费用硬上限。

[PROTOCOL.md](PROTOCOL.md)在首次真实请求前保存；第一轮检查后、问答请求前增补了诊断问题。三项工具和数据是本仓库自有实现，没有依赖上游科研框架、执行模型生成的代码、检索论文或复现论文结果。独立复核实际运行另一种回归公式，从原始数据重算预测及指标，不能仅靠模型说“核验通过”。

原始公开记录：[第一轮评审前](round-01-before-review.json)、[最终完整项目](final-project.json)、[第一轮组会](meeting-01.json)、[第二轮组会](meeting-02.json)。JSON包含实际请求载荷、原始返回、usage、工具参数、数据和证据哈希，不包含请求授权头或 API key。

两轮间增加了独立 `tool_operations` 保存：工具运行后、模型写报告前提交完整结果，即使报告失败也能读回。因此第一轮三份工具结果在不可变角色证据内；第二轮还多了三份独立工具记录，**没有事后伪造第一轮独立记录**。这一存储修订不改变数值算法或模型配置。模型上下文参数修订则在13次请求结束后进行。没有在第一轮前记录完整源码字节哈希；[SOURCE-SHA256.txt](SOURCE-SHA256.txt)仅标识最终受测试版本，不能用它声称两轮执行源码完全相同。

## 离线复查与限制

从仓库根目录运行以下命令均不调用真实模型：

```bash
python3 reproductions/2026-10-06-complete-case/audit_saved_case.py
python3 -W error::ResourceWarning -m unittest discover -s tests -v
node --check labcouncil/static/app.js
```

Python3.11和3.14各 **32项测试通过**，输出见 [3.11](tests-python311.txt)、[3.14](tests-python314.txt)。供应商 HTTP fixture 是离线替身，检查并发次数上限、429、超时、usage缺失、租约过期不重发、报告失败后保留工具结果、篡改数值被复算发现及旧M1数据库升级。它们不能计为真实 Flash 的模型质量结果。离线审计另外核对六份证据哈希、原始指标和 seed7 的训练数据不变、恰好十个测试标签变化。

这次证明一个受控案例可以走完整个平台循环，并揭露报告可靠性缺口。仍未验证：实际用户科研评审、任意idea的实现、文献工具、隔离代码执行、外部实验副作用恢复、长期在线、科研质量改善与人工时间成本。正常停止重启不能代替崩溃窗口或远端去重验收。真实任务中断后的默认策略是保留额度并停止重发；用户人工评审时间保持未知。
