# 持续群聊的执行约定

界面采用同一个消息输入框：讨论、汇报、安排工作、补充条件和暂停都在群里发生。“开组会 / 下一轮方向 / 工作条件”不再是必经入口，初次建群也不要求逐项填写向导。

## 怎样从聊天接着工作

普通提问只产生答复。明确工作指令在现有权限和预算内直接成为安排，并复述目标、时间上限和允许工具。尚未决定的讨论和想法整理为提议，待人类在群里同意后执行；讨论中的假设、模型自己建议和引用资料不授权执行。资源和要求从原安排继承并加入用户补充，权限只能来自人类明确的允许或禁止语句。较复杂的权限表达可能未识别，助手应继续澄清，不自行扩权。

本机确定性控制支持“按这个做 / 同意 / 开始吧”等同意语、“暂停一下 / 先停一下”、“恢复工作”和“取消安排”。这些是自然对话的常见短语，真实后端可处理其他提问与工作请求；模拟后端只用模板与有限规则演示，不冒充模型理解。

在群里同意安排时，后台仍用输入版本隔离工作，保存决策出处和原始输入。如果当前有步骤在执行，已同意安排持久化等待，不启动旧队列的其他步骤；当前步骤完成、失败或租约过期后再交接。已有时间预算不因改方向重置；只有明确补充新时长才在交接时开启新预算，首次尚未启动工作也从交接时计时。暂停也会暂停待交接安排，恢复后继续。后台累计任务、模型、HTTP额度不会重置。

版本、冻结材料和状态仍是记录实现的一部分，用户无需操作这些状态机。现有组会API保留兼容，旧快照和讨论不迁改。

## 如何保留答复依据

每条消息保存当时的输入、任务状态、已有报告和工具结果、近期聊天及旧组会讨论节选。模型仅依据这份消息上下文作答，引用只能来自其中真实证据ID。下一条消息可以使用更新后的报告，不被第一条提问的旧快照锁住。旧消息内容和依据不可覆盖；网页附件可打开原始证据与模型请求。

上下文有长度限制并标注节选：完整历史留在SQLite，模型尚无主动检索所有历史的工具。引用通过校验仅证明引用存在，不能保证推理和每句话正确。没有研究证据时允许讨论状态和规划，不能声称实验完成。

## 故障与重放

同一项目一次处理一条消息。同一编号、同一内容重放返回原结果；改用同编号发不同内容会拒绝。调用前关联消息和模型账本；模型失败或引用检查失败会在群里留下失败答复，不触发新工作，不自动重试。处理中的消息超过四分钟后按中断处理，对应未完成调用记为unknown，原记录保留。

真实后端仍是结构化推理：CLI本身无shell或浏览器权限，平台验证提议，执行器只提供已接入的工具。尚未实现任意上游实验、费用/token硬预算或长周期科研成效验证。

## 回执与实际执行

同意、暂停和条件补充可以由本机控制逻辑立即回执，不一定调用模型。页面明确标注“本机系统回执 / 未调用模型”；实际模型请求展示后台和记录的耗时。工作安排保存、任务排队和worker开始执行是不同状态。时间、权限或累计额度阻止启动时，回执列出阻挡原因，不声称研究已经开始，也不自动补充额度。
