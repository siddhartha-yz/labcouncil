# 控制 agent 投入，分别检查研究进展

2026-10-07。不存在可以直接套到不同研究任务上的通用工作量单位。本平台先采用“投入预算 + 可审查交付”，不把时长、token和文件数合成一个科研进度分。

| 维度 | 适合记录什么 | 能说明什么 |
| --- | --- | --- |
| 投入 | 本轮经过时间、模型调用尝试、公开HTTP请求、已知token | 消耗了多少资源，什么时候应停止追加工作 |
| 交付 | 报告、实际工具结果、实验记录、成功/失败步骤 | 有哪些可审查材料；失败尝试仍有消耗和记录价值 |
| 效果 | 本轮问题是否回答、复现是否通过、独立核验范围、未解决分歧 | 相对于明确目标取得了什么进展，需要按任务验收 |

工作两小时可能解决关键问题，也可能一直报错；token多、读到的论文多或生成文件多，都不能直接当成进展。一个有完整失败日志的实验也可能排除错误方向。验收标准应在规划中明确，组会按实际证据检查，不让agent自己宣布完成百分比。

## 当前实际支持

本轮工作时长是投入上限，默认120分钟，从确认本轮起计算，包含暂停与服务离线；截止不启动新步骤，已启动步骤在租约内收尾。旧组会API确认下一轮会重新计时，草稿不计时；持续群聊中改变方向沿用当前截止，明确给新时长才开启新预算。时间预算不要求agent跑满，原每轮六步上限及资源、权限约束仍有效。

后台模型与公开HTTP上限目前是整个项目累计上限，不是每轮自动补满的预算。组会问答无累计次数上限，仍记录每次尝试。Codex按CLI启动计数，一次可能包含多个内部模型turn；已知usage事后保存，未知保留未知。没有严格的token、费用或GPU时长硬预算，不把CLI启动次数描述成实际API请求数。

群聊设置中的现有执行详情分别显示本轮时间预算、工具结果、报告及失败步骤，保留原调用账本。数量方便审查，不代表研究质量；当前计算仍限已接入工具，尚不能自主执行任意仓库代码或GPU实验。

后续可以按小规模实测，为同类任务给出预算建议。例如“核对三项相关工作并说明验证范围”和“固定环境复现一次基线”分别定义交付标准，再观察各自消耗。现有合成题质量分保持独立，不用于宣称一般科研工作量；不先人为规定“一份README等于多少研究点”。

## 公开方法参考及使用边界

[RE-Bench](https://arxiv.org/abs/2411.15114)比较不同时间预算下的任务成绩，提供投入与产出分别测量的参考。[METR时间视野](https://metr.org/time-horizons/)使用人类专家完成任务所需时间刻画任务难度，并不是agent实际运行时长。[METR指标研究札记](https://metr.org/notes/2026-07-24-metrics-of-model-ability/)讨论固定投入下的得分和达到指定得分所需投入；该札记自述审查程度低于其研究文章，不将其当成已验证的通用标准。

这里借鉴记录和比较方式，尚未复现上述公开评测，没有据此给LabCouncil或任何后端补上成绩。下一步需要固定任务、预算档位、独立验收及多次重复，才能讨论投入增加是否带来有效进展。

持续群聊中的目标修改不重置正在使用的时间预算。明确提出新时长才在安排生效时开启新预算；建群已建立的初始截止时间不因未消耗任务而重置；工具卡明确提交时长属于新预算，生效时起计时。旧组会API确认新轮仍保留原有计时行为。
